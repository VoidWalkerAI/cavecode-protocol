# CaveCode Case Study: The Yoke 3C Conversion

**Date:** May 17, 2026
**Subject:** ESP32 Grain Bin Tracker (Arduino/C++)
**Protocol:** CaveCode v1.1
**Author:** Claude (Anthropic) for SageWire Syndicate LLC

---

## Project Context

**The Yoke 3C** is a real-world farm tool built by SageWire Syndicate to solve a specific operational problem: tracking the running balance of a 15-ton grain bin without internal sensors. The device uses an ESP32 microcontroller paired with a Bluetooth Kunhong crane scale to weigh bags as they're filled from the bin, automatically subtracting each bag's weight from a running total stored in persistent memory.

The original code was generated by ChatGPT and tested in production on a working farm. It functions correctly—handles BLE reconnection, persists data through power cycles, hosts its own WiFi access point with a captive portal, and includes session management with undo functionality. The codebase is approximately 350 lines of Arduino-style C++ mixed with embedded HTML/CSS/JavaScript.

This case study documents the conversion of the existing functional codebase into CaveCode v1.1 format—the protocol developed by SageWire to prevent AI-induced code drift during collaborative development.

---

## Why CaveCode for Embedded Code?

CaveCode was originally designed and tested on HTML/JavaScript applications (HerdMate, TagReaper, Cobra Commander tribute page, the CaveCode Arcade). This conversion demonstrates that the protocol is **language-agnostic**—it works on Arduino/C++ embedded systems just as effectively as web applications.

The same problems that affect HTML edits affect embedded code:
- AI assistants tend to rewrite entire files when asked for small changes
- Configuration values get scattered through logic blocks
- User-facing strings become entangled with control flow
- Comments document the wrong things, leaving operational context unclear

CaveCode addresses all of these for any language with comment support.

## The Five Blocks (As Applied)

### 🧱 Block 1 — IDENTITY [LOCKED]

The structural foundation: library imports, hardware pin definitions, global object declarations, BLE UUIDs, state variables, and the embedded HTML template for the web UI. These elements rarely change during normal feature development—they define what this device *is*, not what it *does*. By locking this block, the protocol prevents accidental damage to the device's core identity.

**What was placed here:**
- All `#include` directives
- `LED_PIN` definition
- BLE service/characteristic UUIDs
- Global object instances (`WebServer`, `DNSServer`, `Preferences`, BLE clients)
- All state-tracking variables (weights, flags, timestamps)
- The complete embedded HTML/CSS/JavaScript web interface as a `PROGMEM` string literal

**Why locked:** Changing any of this risks breaking the device entirely. The HTML in particular is large and easy to corrupt during careless edits.

### 🖍️ Block 2 — TUNING KNOBS [Human Edit Zone]

All numerical and configuration values that operators might legitimately want to adjust were extracted into a single, clearly-labeled section.

**What was placed here:**
- WiFi access point credentials (`AP_NAME`, `AP_PASS`)
- Scale identification (`SCALE_MAC`)
- Weight detection thresholds (`LOCK_MIN_LB`, `LOCK_TOLERANCE_LB`, `LOCK_TIME_MS`, `ZERO_THRESHOLD_LB`)
- The kilogram-to-pound conversion constant (`KG_TO_LB`)

**Why this matters:** In the original code, these values were scattered—some near the top of the file, others embedded inside `parseScale()`, others as hardcoded literals inside function calls. A farmer wanting to tune the sensitivity of the weight-lock detection had to read through unrelated logic to find them. Now they're in one place.

### 🌐 Block 3 — PUBLIC TEXT [Human Safe Zone]

All user-facing strings—the status messages displayed in the web UI—were extracted into named constants.

**What was placed here:**
- Every status message string (`"BOOTING"`, `"SCANNING"`, `"BAG LOCKED - REMOVE BAG"`, etc.)
- These became `MSG_BOOTING`, `MSG_SCANNING`, `MSG_BAG_LOCKED`, etc.

**Why this matters:** In the original code, these strings were hardcoded inline throughout the logic. Changing "BAG LOCKED - REMOVE BAG" to a different message required finding it inside `updateWeightLock()`. Now a farmer or translator can edit Block 3 without touching any logic, and a non-English speaker could localize the entire UI without risk.

### 🎮 Block 4 — BEHAVIOR [Logic Engine]

All operational logic—the functions that make the device actually work.

**What was placed here:**
- Weight parsing (`parseScale`)
- Weight-lock detection (`updateWeightLock`)
- Auto-log on bag removal (`checkAutoLogAfterRemoval`)
- BLE scanning and connection (`scanForScale`, `connectScale`)
- Web server endpoints (all `server.on(...)` handlers)
- The `setup()` and `loop()` functions

**Why this matters:** This is the only block where logic changes happen. When debugging or adding features, the developer (or AI) knows exactly where to look and where to make changes. Block boundaries prevent logic from bleeding into UI strings or configuration.

### 📝 Block 5 — HUMAN NOTES [Open]

Operational documentation written in plain language for future maintainers.

**What was placed here:**
- Purpose statement
- Workflow walkthrough
- Hardware requirements
- Network architecture
- Future expansion plans
- Known limitations
- Version history

**Why this matters:** This information was completely absent from the original file. Anyone reading the code six months from now—or any AI being asked to help with the next iteration—now has full context without needing to ask.

## What Changed (And What Didn't)

### What changed:
- **Configuration values** centralized into Block 2
- **UI strings** extracted into named constants in Block 3
- **Logic references** updated to use named constants instead of inline literals (e.g., `stateText = MSG_SCANNING` instead of `stateText = "SCANNING"`)
- **Operational documentation** added in Block 5
- **Block headers and boundaries** added throughout to enforce structural integrity

### What did NOT change:
- **No logic was modified**
- **No functions were renamed**
- **No behavior was altered**
- **No control flow was changed**
- **The HTML interface is byte-for-byte identical**
- **All API endpoints work identically**
- **BLE pairing behavior is unchanged**
- **Persistent storage keys are unchanged** (so existing devices won't lose their bin balance after upgrade)

This is the core promise of CaveCode: **organize without altering**. The device behaves identically. Only the code's structural clarity has improved.

## Drift Analysis

The original code had specific risks that CaveCode mitigates:

| Risk in Original | CaveCode Mitigation |
|---|---|
| Tuning a threshold required hunting through logic | Block 2 centralizes all knobs |
| Editing a UI message risked typo in critical code path | Block 3 isolates text from logic |
| AI asked to "improve" the code could rewrite entire file | Block 1 lock prevents core changes |
| New developer had no operational context | Block 5 documents purpose and plans |
| Adding features risked breaking unrelated functionality | Block boundaries enforce locality of change |

When the next iteration is needed—adding multi-bin support, cloud sync, herd tagging—the developer or AI will know:
- Multi-bin support is a Block 1 change (new structural elements)
- Cloud sync endpoints go in Block 4 (new behavior)
- New status messages go in Block 3 (new text)
- New tuning values go in Block 2 (new knobs)
- Updated documentation goes in Block 5

Each future change has a natural home. Drift becomes structurally difficult.

## Broader Implications

This conversion is the **first documented CaveCode application to embedded C/C++ on a microcontroller platform**. Previous demonstrations have been web technologies (HTML/CSS/JavaScript). This proves the protocol's portability claim: CaveCode is not a web standard, a JavaScript convention, or an Arduino pattern. It is a **general-purpose code organization protocol** that uses comment-based block markers, which means it works in any language that supports comments.

**Languages where CaveCode should work without modification:**
- C, C++, C# (block comments and line comments)
- Java, Kotlin, Swift
- Python (with `#` and triple-quote sections)
- JavaScript, TypeScript
- Go, Rust
- Ruby, PHP
- HTML, CSS (with `<!-- -->` and `/* */`)
- Shell scripts, PowerShell
- SQL (with `--` and `/* */`)
- Configuration files (YAML, TOML, INI with their comment styles)

The Yoke 3C conversion validates that the protocol scales beyond its origin domain.
