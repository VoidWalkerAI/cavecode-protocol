============================================================
🪨 BLOCK 1 — WHAT CAVECODE IS
============================================================

CaveCode is a plain-text human/AI map for software,
systems, tools, hardware, games, workflows, and other
structured projects.

CaveCode is not a programming language.

The implementation tells the machine what to do.

CaveCode helps the human or AI understand:

- what the system is
- how it is organized
- what is safe to change
- what should be protected
- where important behavior lives
- what can be expanded
- what may be exposed publicly
- what has already been decided
- what remains unfinished
- how to resume the work later

CORE PURPOSE:

Make complicated work understandable, editable,
transferable, and restartable without requiring the
next person or AI to reconstruct the entire project
from old conversations.


============================================================
🪨 BLOCK 2 — CANONICAL GLYPH VOCABULARY
============================================================

The five standard CaveCode glyphs are:

🪨 Locked Block
    Protected structure, rules, invariants, or material
    that should not be casually changed.

🖍️ Human Edit Zone
    Material intentionally safe and accessible for
    human editing.

🔧 Expandable Block
    Extensions, future work, optional features,
    experiments, or intentionally open areas.

🎮 Game Logic Block
    Behavior, mechanics, flow, processing, state
    transitions, or other operational logic.

🌐 Public-Safe Block
    Material intended or approved for public-facing use.

RULE:

These glyphs describe SEMANTIC ROLES.

They do not represent five mandatory positions in a file.


============================================================
🪨 BLOCK 3 — BLOCK MODEL
============================================================

CaveCode does not have a fixed number of blocks.

Use as many blocks as the artifact requires for clarity.

The five standard glyphs may be reused any number of times.

Example:

    🪨 BLOCK 1 — SYSTEM IDENTITY
    🎮 BLOCK 2 — MAIN FLOW
    🎮 BLOCK 3 — ERROR HANDLING
    🖍️ BLOCK 4 — USER SETTINGS
    🖍️ BLOCK 5 — CALIBRATION
    🌐 BLOCK 6 — PUBLIC MESSAGES
    🔧 BLOCK 7 — FUTURE INTEGRATIONS
    🎮 BLOCK 8 — RECOVERY FLOW
    🪨 BLOCK 9 — AUTHORITY RULES

MODEL:

Block number = location / address.

Glyph = semantic role.

Block title = specific subject.

GUIDELINE:

Prefer one primary glyph per block.

If one block contains substantially different semantic roles,
consider splitting it into multiple blocks instead of making
the meaning ambiguous.


============================================================
🪨 BLOCK 4 — RESTARTABILITY AND HANDOFF
============================================================

CaveCode must help solve the START-AND-STOP PROBLEM.

Projects are interrupted.

People forget context.

AI sessions end.

Another human or AI may eventually inherit the work.

A useful CaveCode project should allow someone to return
later and determine, without reconstructing old conversations:

- What is this?
- What currently works?
- What is protected?
- What may safely be changed?
- What important decisions are settled?
- Why were those decisions made?
- What was tried and failed?
- What is currently broken?
- What remains uncertain?
- What should happen next?
- Where can deeper information be found?

CaveCode should preserve enough context that work can
outlive the session, device, AI model, or person that
originally created it.


============================================================
🪨 BLOCK 5 — PROJECT MEMORY STRUCTURE
============================================================

CaveCode projects use layered memory.

LAYER 1 — MASTER MAP

    CAVECODE-PROTOCOL.cavecode.txt

    Answers:

    "Where are we now?"

    Contains:
    - current project state
    - settled decisions
    - unresolved questions
    - known contradictions
    - resume point
    - pointers to deeper material


LAYER 2 — LOCAL CAVECODE MAPS

    Major subsystems may have their own CaveCode files.

    Examples:

    tools/validator/VALIDATOR.cavecode.txt
    tools/compiler/COMPILER.cavecode.txt
    tools/fixer/FIXER.cavecode.txt

    Answers:

    "How does this particular part work?"


LAYER 3 — HISTORY

    cavecode-builders-log.md
    Git commits and repository history

    Answers:

    "How did we get here?"

    Historical records should not be silently rewritten merely
    because current thinking changes.

    Current maps describe present truth.
    Historical records preserve the path.


============================================================
🎮 BLOCK 6 — HANDOFF CHECKPOINT
============================================================

Before intentionally stopping a meaningful work session,
update the appropriate CaveCode map.

Record, when applicable:

WHAT CHANGED?

WHAT WAS DECIDED?

WHY WAS IT DECIDED?

WHAT WAS TRIED AND FAILED?

WHAT CURRENTLY WORKS?

WHAT IS CURRENTLY BROKEN?

WHAT REMAINS UNCERTAIN?

WHAT FILES OR SUBSYSTEMS WERE AFFECTED?

WHAT SHOULD HAPPEN NEXT?

WHAT IS THE NEXT HUMAN OR AI MOST LIKELY TO MISUNDERSTAND?

Do not duplicate Git unnecessarily.

Git records what changed in the files.

CaveCode should preserve the meaning, reasoning,
state, and handoff information around those changes.

🪨 BLOCK 7 — SETTLED DECISIONS
============================================================

DECISION CC-001

The original five CaveCode glyph meanings remain the
canonical semantic vocabulary:

🪨 Locked Block
🖍️ Human Edit Zone
🔧 Expandable Block
🎮 Game Logic Block
🌐 Public-Safe Block

WHY:

They communicate how a human or AI should understand
and interact with a section.


DECISION CC-002

There is no hard maximum number of CaveCode blocks.

WHY:

Different systems require different amounts of structure.


DECISION CC-003

Standard glyphs may be reused across multiple blocks.

WHY:

Glyph = semantic role.
Block number = location.
Block title = specific subject.


DECISION CC-004

Restartability and handoff are first-class CaveCode goals.

WHY:

A project should be resumable after an interruption
without requiring reconstruction of lost conversation context.


DECISION CC-005

CaveCode project memory will use three layers:

1. Master map
2. Local subsystem maps
3. Builder's Log + Git history

WHY:

No single memory mechanism is reliable enough by itself.


DECISION CC-006

The preferred human-facing CaveCode filename convention is:

    *.cavecode.txt

Examples:

    CAVECODE-PROTOCOL.cavecode.txt
    FATECASTER.cavecode.txt
    VALIDATOR.cavecode.txt

WHY:

CaveCode must be readable with ordinary text-reading tools.

The standalone .cavecode extension is not recognized by
many ordinary mobile applications.

The protocol must not require a dedicated CaveCode application
merely to read a CaveCode artifact.

A bare .cavecode file may still be used by tools, developers,
or environments that support it.

The contents remain plain UTF-8 text.


DECISION CC-007

A repository managed with CaveCode keeps one root-level
*.cavecode.txt file as its read-first Master Project Map.

WHY:

The project state must live with the work rather than depend
on access to an old conversation.


DECISION CC-008

The Master Project Map is authoritative for current project
understanding and current human decisions recorded there.

Deeper ratified contracts remain authoritative for their
specific subjects. Conflicts must be reconciled explicitly.


DECISION CC-009

A meaningful project-state change is incomplete until the
Master Project Map is updated in the same commit.

WHY:

The repository should be understandable immediately after
the commit, not after a separate documentation repair.


DECISION CC-010

Project maps distinguish planned, implemented, tested,
committed, deployed, superseded, and rejected states when
those distinctions matter.

Future work may be forecast, but it must not be described as
completed before it is true.


DECISION CC-011

Subsystem maps are permitted when they declare their scope
and point back to the repository Master Project Map.

They must not quietly become competing master truths.


DECISION CC-012

A Master Project Map must provide a cold-start resume point.

A human or AI without prior chat history should be able to
determine what the project is, what is true now, what is
protected, what remains unresolved, and what happens next.

============================================================
🌐 BLOCK 11 — PUBLIC-SAFE SHORT DESCRIPTION
============================================================

CaveCode is a plain-text human/AI mapping protocol
for making software and systems easier to understand,
modify, hand off, and resume.

It uses simple reusable glyphs and labeled blocks to show
what is protected, what humans may safely edit, where
behavior lives, what can be expanded, and what is intended
for public use.

CaveCode sits with or beside the implementation.
It does not replace the programming language underneath it.
